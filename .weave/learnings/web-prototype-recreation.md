# Learnings: Web Prototype Recreation

## Task 2: Restyle Atlas tokens and shadcn-style/Solid UI primitives
- **Discrepancy**: The plan assumed browser proof could capture interactive overlay states directly from `/dev/design-system`, but the existing app has a pre-existing TanStack Start/Solid hydration error (`template2 is not a function`) that disables client-side interactivity even on untouched routes.
- **Resolution**: Added an SSR-safe proof path by rendering the real dialog inline and opening it from the `?overlay=open` search param so overlay parity could be captured without relying on broken hydration.
- **Suggestion**: Future UI tasks should not assume client interactivity is available until the hydration issue is explicitly addressed; use SSR-renderable states or dedicated proof variants whenever overlay/open-state screenshots are required.

## Task 4: Build the routed Inbox workspace vertical slice
- **Discrepancy**: The plan required tablet/mobile inbox screenshots that preserve visible functionality, but the source prototype has no responsive breakpoints and simply overflows its fixed three-column grid at smaller sizes; the same pre-existing hydration error also prevented proving row selection and toolbar toggles through live clicks.
- **Resolution**: Implemented Atlas-scoped responsive reflow rules for the app version at smaller breakpoints and used SSR search-param variants (`sel`, `setAside`, `replyLater`) on `/atlas/inbox` to prove selection/toggle states without relying on broken client hydration.
- **Suggestion**: Future route tasks should explicitly distinguish desktop parity requirements from small-screen functional adaptations, and should plan SSR-proof variants up front while the hydration bug remains unresolved.

## Task 5: Implement onboarding entry and replay flow
- **Discrepancy**: The plan listed `apps/web/src/routes/atlas.tsx` for `/atlas`, but with TanStack file-based routing the dedicated `/atlas` entry screen had to be implemented in `apps/web/src/routes/atlas/index.tsx` while keeping `atlas.tsx` as the parent layout route; the plan also expected `app_state.ts` edits even though Task 3 had already provided the needed `ONBOARDING_STEPS` data unchanged.
- **Resolution**: Added `apps/web/src/routes/atlas/index.tsx` for the first-run onboarding route, kept `atlas.tsx` as the `<Outlet />` layout, added `/atlas/onboarding` replay, and consumed the existing `ONBOARDING_STEPS` fixture directly without modifying `app_state.ts`.
- **Suggestion**: Future TanStack route tasks should specify layout-route files and index-route files separately, and should distinguish between files that must change versus existing data modules that are only dependencies.

## Task 6: Implement Screener route and accept/reject local behavior
- **Discrepancy**: The plan's file list did not mention that stateful Screener↔Inbox navigation and accepted-item visibility would also require updates to `apps/web/src/routes/atlas/inbox.tsx`, `apps/web/src/components/atlas/atlas_app.tsx`, and shared route-link behavior in the sidebar while hydration remains broken.
- **Resolution**: Kept the same SSR/search-param proof strategy by serializing screener decisions into `?d=` tokens, then threaded that state through `/atlas/screener`, `/atlas/inbox`, `SidebarNav`, and `AtlasApp` so accepts/rejects, nav counts, and accepted inbox insertion all work server-side without client JS.
- **Suggestion**: Future cross-route Atlas tasks should explicitly call out any already-built routes/components that must preserve shared search-param state, especially while broken hydration forces link-driven interaction proofs.

## Task 7: Implement Feed and Paper Trail routes
- **Discrepancy**: The plan listed several shared workspace components and `app_state.ts` as expected edits, but those abstractions from Task 4 were already sufficiently view-agnostic; the actual missing piece was a shared mail-route link resolver plus small route updates so `?d=` screener state survives across all mail destinations.
- **Resolution**: Added new route files for `/atlas/feed` and `/atlas/paper-trail`, introduced `apps/web/src/lib/atlas/nav_links.ts` to centralize SSR-proof mail navigation, and refactored `inbox.tsx`/`screener.tsx` to reuse that resolver while leaving `mail_workspace.tsx`, `mail_list.tsx`, `mail_row.tsx`, `thread_view.tsx`, `sidebar_nav.tsx`, and `app_state.ts` unchanged.
- **Suggestion**: Future reuse-heavy tasks should separate "expected dependencies" from "must-edit files" and should call out shared navigation/state plumbing explicitly when a new route must preserve cross-screen URL-carried state.

## Task 8: Implement Tasks & Dates route
- **Discrepancy**: The plan expected edits to `sidebar_nav.tsx` and `sample_data.ts`, but both were already sufficient from earlier tasks; the real implementation work required a new full-pane route/screen/card set plus extending the shared `nav_links.ts` resolver so the Assist link could route while preserving `?d=` state. The live prototype also overrides `--font-heading` to `Space Mono` at runtime on this screen, which conflicts with Atlas's Bungee heading token from `DESIGN.md`.
- **Resolution**: Added `/atlas/tasks`, `tasks_screen.tsx`, `task_card.tsx`, `date_card.tsx`, Atlas-scoped task/date styles, and expanded `nav_links.ts` to include the Tasks route while leaving fixture data and sidebar component code unchanged. Kept Bungee headings to stay consistent with the Atlas design system, and documented that accepted desktop residual as a token-spec divergence rather than a structural mismatch.
- **Suggestion**: Future plan steps should distinguish between prototype quirks that should be copied literally versus places where `DESIGN.md` intentionally overrides the prototype, and should list shared route-link infrastructure when a newly routed Assist screen must become reachable from existing sidebars.

## Task 9: Implement Settings route and interactive toggles
- **Discrepancy**: The plan again listed `sidebar_nav.tsx` as a target edit, but the existing sidebar abstraction was already sufficient; the actual routing work belonged in the shared `nav_links.ts` resolver. The task also assumed live toggle-click proof would be available, but the unresolved hydration bug still blocks event handlers, so proving independent toggle persistence required shared SSR-safe visual binding in the `Toggle` primitive itself.
- **Resolution**: Added `/atlas/settings`, `settings_screen.tsx`, `settings_row.tsx`, Atlas-scoped settings styles, extended `nav_links.ts` to route Settings, and hardened `components/ui/toggle.tsx` so its resting thumb position is driven by `data-on` in CSS while keeping Motion for hydrated animation. That made deterministic local-state proof possible without a Settings-specific styling fork.
- **Suggestion**: Future interactive-route tasks should explicitly call out when a shared primitive must gain SSR-safe visual-state behavior to support proof under broken hydration, and should avoid listing already-sufficient sidebar components as required edits when routing is really handled by shared link plumbing.

## Task 10: Implement Compose overlay and reply prefill
- **Discrepancy**: The plan listed `top_bar.tsx`, `dialog.tsx`, and `input.tsx` as target files, but the existing topbar compose trigger contract and shared dialog/input primitives were already sufficient; the real missing work was composing overlay state through `AtlasApp`, threading reply sender context from `ThreadView`, and adding an SSR-proof `?compose=` route variant because hydration still blocks live open-state proof. The live prototype also has a quirk where the topbar compose action reuses the selected thread's reply prefill instead of opening a truly blank new-message state.
- **Resolution**: Added `compose_dialog.tsx`, threaded compose mode and reply sender state through `AtlasApp`/`MailWorkspace`/`ThreadView`, added `decodeComposeMode()` plus `/atlas/inbox?compose=new|reply` SSR proof support, and reused the existing shared `Dialog` and `Input` primitives unchanged with scoped compose-only CSS overrides. Kept the recreation aligned to the task spec by making topbar Compose open a blank new-message overlay while Reply opens the prefilled draft.
- **Suggestion**: Future overlay tasks should distinguish between files that must change versus primitives that are only reused, and should call out when the recreation should intentionally follow the written product requirement instead of copying a prototype quirk literally.

## Task 11: Implement Assistant overlay, canned chat, citations, and shortcuts
- **Discrepancy**: The plan listed `assistant_responses.ts`, `app_state.ts`, `top_bar.tsx`, `dialog.tsx`, and `input.tsx` as target edits, but those shared modules were already sufficient. The actual missing work was a new assistant overlay component, wiring assistant state and document-level shortcut handling through `AtlasApp`, adding citation deep-link routing that preserves `?d=` state, and creating SSR-proof `?assistant=` / `?ask=` variants because broken hydration still blocks live keyboard and submit proof.
- **Resolution**: Added `assistant_dialog.tsx`, extended `AtlasApp` with assistant-open state plus `resolveShortcut`-driven key handling and citation-link serialization, added `atlasCiteLinkFor()` in `nav_links.ts`, extended `/atlas/inbox` search params with `assistant` and `ask`, and reused the existing canned-response data, topbar contract, dialog/input primitives, and shortcut resolver unchanged.
- **Suggestion**: Future keyboard/overlay tasks should separate shared dependencies from must-edit files, and should explicitly budget for SSR-proof variants plus deep-link routing helpers whenever hydration limitations prevent validating live shortcut and citation flows directly.

## Task 12: Harden full responsive parity across all completed Atlas routes
- **Discrepancy**: The plan anticipated broad shared-component edits across many Atlas surfaces, but the existing responsive layer from Tasks 4–11 was already largely sufficient. The only real regression uncovered in the cross-route audit was a tablet-landscape clipping issue in the shared thread toolbar, where the narrowed pane caused the Prev/Next button group to overflow and become unreachable.
- **Resolution**: Kept the responsive work centralized in `apps/web/src/styles.css` and fixed the regression with a scoped `@media (max-width: 1100px)` wrap rule for `.atlas-thread-toolbar`, preserving desktop geometry while restoring toolbar reachability at tablet widths. Verified the full 9-surface × 4-breakpoint screenshot matrix, overlay seeded states, no-overflow guarantees, reduced-motion behavior, and resize safety without touching the already-sufficient component markup.
- **Suggestion**: Future responsive-pass tasks should distinguish between an audit/verification sweep and expected implementation-heavy edits, and should call out that a shared-style-only fix is acceptable when the component structure is already correct.

## Task 13: Run final verification, proof index, and PR handoff
- **Discrepancy**: The plan scoped Task 13 to a final proof manifest, but the final clean-tree / PR-handoff requirement also forced cleanup of a stale generated `apps/web/src/routeTree.gen.ts` artifact and formal commits for previously uncommitted supporting docs/prototype/design/spec/weave files that had accumulated during plan execution. The live browser smoke also could not validate hydrated shortcuts directly because the pre-existing `template2 is not a function` error still blocks client interactivity.
- **Resolution**: Regenerated and committed `routeTree.gen.ts` so tracked output matches the current toolchain, committed the accumulated supporting artifacts in focused conventional commits, used SSR-proof URLs plus source-level shortcut verification for the final smoke, pushed `feat/spec-02-web-prototype-recreation`, and recorded PR `https://github.com/josevelaz/atlas/pull/28` in the final manifest.
- **Suggestion**: Future plans should explicitly note when generated files are expected to be committed after build verification, and should separate product-surface tasks from repo-hygiene/documentation artifacts that are required to satisfy a final clean-tree handoff.
