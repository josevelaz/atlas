## What shipped

The Feed and Paper Trail category screens are now routed, reusing the **shared
Atlas mail workspace** end to end — only the `view` differs from `/atlas/inbox`:

- **`/atlas/feed`** — the Feed category (newsletters, marketing, browse-later).
  List header reads **"The Feed"** (via `listTitle("feed")`), no AI banner
  (inbox-only), category count = `feedList(decisions).length`.
- **`/atlas/paper-trail`** — the Paper Trail category (receipts, confirmations,
  shipping notices). List header reads **"Paper Trail"**, no AI banner, count =
  `paperList(decisions).length`.

Both screens render through the same `AtlasApp` → `AppShell` (TopBar +
SidebarNav) → `MailWorkspace` (MailList + ThreadView) pipeline as the inbox, so
row treatments (avatar / sender / subject / 2-line preview clamp / unread dot /
selected = yellow fill), priority + tag chips, right-aligned time metadata,
empty-list state, and no-thread-selected pane behavior are byte-for-byte the same
shared components — no Feed/Paper-specific UI was forked.

### Per-category selection

Selection is owned per category in `SelectionState` (`{ inbox, feed, paper }`).
`/atlas/feed?sel=<id>` seeds `selected.feed`; `/atlas/paper-trail?sel=<id>` seeds
`selected.paper`. The `MailWorkspace` already reads `selectedId` off the active
`view`, so each screen tracks its own selection independently. By default
`selected.feed` / `selected.paper` are `null` (per `createInitialState`), so both
screens open with the **"No thread selected"** pane — matching the prototype,
where only the inbox pre-selects `i1`.

### Accepted screener items route to Feed / Paper Trail

The pre-existing `acceptedExtras` / `feedList` / `paperList` derivation already
prepends synthetic mail rows produced by accepted screener items. Feed and Paper
Trail consume those lists unchanged, so an item accepted into Feed
(`?d=s2:feed`) or Paper Trail (`?d=s3:paper`) appears at the **top** of the
respective list with the correct styling (Feed extras carry `unread: true`;
Paper extras are read), and the sidebar counts re-derive accordingly.

### Cross-screen SSR-proof navigation (shared `?d=`)

Client hydration is disabled by the documented pre-existing TanStack Start/Solid
error (`template2 is not a function`), so navigation is `<a href>`-driven and
server-rendered. A new shared resolver `atlasMailLinkFor(d)` (in
`lib/atlas/nav_links.ts`) routes **all four** mail destinations (Screener /
Inbox / Feed / Paper Trail), each carrying the current `?d=` decision string.
The inbox and screener routes were refactored to use the same resolver (they
previously only routed Inbox ↔ Screener), so the sidebar now links between every
mail screen and the screener `?d=` state is preserved across all of them.

`/`, `/dev/design-system`, `/atlas/onboarding` are untouched (200, no workspace
CSS leak). No React patterns/imports; no runtime imports from
`docs/prototype/**`. `routeTree.gen.ts` was regenerated by the dev server (not
hand-edited).

## Responsive (tablet / mobile)

| Viewport | Screen | Mean diff vs proto | Within 14/255 |
|---|---|---|---|
| 1024×768 | feed | 16.67 | 86.3 % |
| 1024×768 | paper-trail | 15.83 | 86.6 % |
| 768×1024 | feed | 25.62 | 77.5 % |
| 768×1024 | paper-trail | 25.11 | 78.0 % |
| 390×844 | feed | 36.08 | 67.8 % |
| 390×844 | paper-trail | 36.17 | 67.8 % |

The **prototype has no responsive breakpoints** — at narrow widths it keeps its
fixed `240px 380px 1fr` (~1240px) grid, which overflows and is clipped at the
viewport edge. The app reflows (the shared `≤860px` rule from Task 4 stacks the
regions into a single `minmax(0, 1fr)` column). That structural difference (app
stacked vs prototype clipped fixed-grid) is the entire source of the higher
tablet/mobile diffs — the same acceptance-allowed adaptation documented for the
Task-4 inbox, Task-5 onboarding, and Task-6 screener.

**No-clip / fully-functional proof:**

| Check | Feed | Paper Trail |
|---|---|---|
| `body.scrollWidth == innerWidth` @ 390 | 390 == 390 | 390 == 390 |
| `body.scrollWidth == innerWidth` @ 768 | 768 == 768 | 768 == 768 |
| Mail rows rendered @ 390 | 7 | 7 |

No horizontal overflow at any width; every row stays in-bounds.
