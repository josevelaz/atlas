### Accept/reject under broken hydration (SSR-proof, link-driven)

The app has a documented pre-existing TanStack Start/Solid hydration error
(`template2 is not a function`) that disables client interactivity on **all**
routes. Per the Task-2 / Task-4 / Task-5 SSR-proof pattern, every Accept /
Reject and every Screener↔Inbox nav is therefore a `<Link>` that renders a real
`<a href>` server-side. Cumulative decisions are owned by the route via a
compact `?d=` search-param token string:

- `id:category` for an accept (e.g. `s1:inbox`)
- `id:x` for a reject (e.g. `s4:x`)
- joined by commas (e.g. `s1:inbox,s2:feed,s3:paper,s4:x`)

`decodeDecisions` / `encodeDecisions` (new in `app_state.ts`) translate this
string ⇄ `ScreenerDecisions`, which feeds the same pure derivation helpers the
inbox slice already used. Every transition is observable in server-rendered
HTML and works without JS. The underlying handlers are standard Solid
signal-backed search-param reads; they execute identically on the client once
the app-wide hydration error (out of scope for this task) is resolved.

## Responsive (tablet / mobile)

| Viewport | State | Mean diff vs proto | Within 14/255 | Notes |

| 1024×768 | initial | 24.55 | 78.8 % | App reflow begins; cards/colors/borders match. |

| 768×1024 | initial | 46.21 | 48.8 % | **Documented adaptation** (below). |
| 768×1024 | empty | 18.32 | 84.9 % | Empty box centered; reflow vs fixed-grid proto. |
| 390×844 | initial | 47.47 | 46.7 % | **Documented adaptation** (below). |
| 390×844 | empty | 27.10 | 77.1 % | Empty box centered; reflow vs fixed-grid proto. |

The **prototype has no responsive breakpoints** — at narrow widths it keeps its
fixed `240px 380px 1fr` (~1240px) grid, which overflows and is clipped at the
viewport edge (it shows the sidebar + the start of the screener column). The app
instead reflows: at `≤860px` the regions stack into a single `minmax(0, 1fr)`
column and the screener column fills the width. That structural difference (app
stacked vs prototype clipped fixed-grid) is the source of the higher tablet /
mobile initial diffs — the same acceptance-allowed pattern documented for the
Task-4 inbox and Task-5 onboarding.

**No-clip / fully-functional proof at mobile (390×844):**

| Check | Result |
|---|---|
| `body.scrollWidth == innerWidth` | 390 == 390 (no horizontal overflow) at 1024 / 768 / 390 |
| Screener cards rendered | 4 |
| Accept links rendered | 4 |
| Reject links rendered | 4 |
| Card fits viewport | card `scrollWidth` = 362px (inside 390px) |

To get there, the mobile rule (`@media max-width: 560px`) constrains the screener
column to the viewport, shrinks intro padding, and **stacks the Accept / Reject
bars vertically** (so the "ACCEPT INTO <CATEGORY>" label no longer forces the
fixed-width card to overflow). The `≤860px` grid was also widened to
`minmax(0, 1fr)` and long mono addresses/names truncate with ellipsis, so every
control stays reachable in-bounds. Desktop parity is unchanged.
