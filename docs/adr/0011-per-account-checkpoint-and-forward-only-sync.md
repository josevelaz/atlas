# Per-account checkpoint and forward-only sync

Each Connected Account carries its own forward-only sync checkpoint (Gmail `historyId`), created at connect time. A connection is considered successful only when both the account and its initial checkpoint are persisted; an immediate catch-up sync then runs from that checkpoint so new mail appears without waiting for push delivery. Registering the Gmail watch/push channel happens asynchronously after that: if registration fails, the account enters a visible degraded state and is retried automatically, but the connection itself does not fail and catch-up polling keeps the account current in the meantime.

The checkpoint only ever moves forward. If Gmail reports the stored `historyId` as expired or otherwise unusable (a history gap), the checkpoint is reset to the mailbox's current position and sync resumes from there — we never backfill the missed window. This extends ADR 0003's new-mail-only stance into steady-state operation: a gap behaves like a fresh connect, not a trigger for historical import. The trade-off is that mail arriving inside a gap is silently absent from Atlas, and per-account checkpoints mean a multi-mailbox user can have accounts in different sync states. We accept this because forward-only recovery is simple, idempotent, and cheap, whereas backfill logic would reintroduce all the cost, privacy exposure, and retroactive-Screener problems that new-mail-only sync was chosen to avoid.
