# Metadata-first ingestion with lazy bodies

Ingestion stores message metadata and a short text preview, not full content. Headers, participants, labels, thread linkage, and the preview snippet are persisted at sync time; full message bodies and attachment bytes are fetched from Gmail only when actually needed — when a thread is opened or a feature such as summarization requires the content — and the fetched content is cached in S3 so each body is pulled from the provider at most once. This keeps the ingest path fast and small (a checkpoint catch-up touches metadata only), bounds storage to content users actually engage with, and aligns with ADR 0002's need-based processing: Atlas does not hold a full copy of mail nobody has looked at.

Lazy fetching requires a live connection. A disconnected account can never fetch, so threads whose bodies were never cached render preview-only, with an explanation that reconnecting the account restores full content; bodies already cached in S3 remain readable. The trade-off is a fetch latency hit on first open, a hard dependency on provider availability for uncached content, and the disconnected preview-only degradation. We accept this because the alternative — eagerly mirroring every body and attachment — multiplies storage cost and privacy exposure for content that is mostly never opened.
