# Use staged production and gated PR previews

The deployment uses three environment classes: staging, production, and ephemeral pull request previews. Staging and production are long-lived; previews are created only for same-repository pull requests with the exact `preview` label and are updated when labeled PRs receive new commits. Preview infrastructure is destroyed when the label is removed or the pull request closes, with scheduled cleanup as a backstop for orphaned resources. Fork pull requests never receive AWS credentials, protected secrets, Turso tokens, or privileged preview deployment permissions.

All environments run in a single AWS account with strict IAM separation by environment and preview. Production and non-production use separate VPCs with no peering; staging and previews run in the non-production VPC. Terraform state is separated by backend key for each long-lived environment and each preview, such as `infra/staging/terraform.tfstate`, `infra/production/terraform.tfstate`, and `infra/previews/pr-<number>/terraform.tfstate`. Production uses production-scoped resources, while staging and previews share non-production infrastructure only where isolation is preserved by IAM, network boundaries, tags, paths, and prefixes.

Each preview receives an isolated Turso database seeded only from a sanitized template, never from live production or staging data. Previews share the staging ElastiCache Redis deployment in the non-production VPC using per-environment key prefixes, and they use the non-production S3 bucket with per-environment and per-preview prefixes. The preview safety model is split into two workflows: an unprivileged `pull_request` workflow that can run for all PRs without credentials, and a privileged, approval-gated preview deployment workflow that checks same-repository source, exact `preview` label, and trusted actor permission before requesting AWS credentials.
