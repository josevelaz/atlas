# Initial-ingest-only provider state

Provider-side spam, trash, and deletion state is evaluated exactly once, at initial ingest. A message arriving with Gmail's spam label is routed to Atlas's Spam queue; messages already trashed or deleted at ingest time are skipped. After that decision, the provider's opinion no longer matters: once a thread is admitted into Atlas, later provider-side changes — the user spamming, trashing, or deleting it in Gmail, or Gmail reclassifying it — never remove it from Atlas or re-route it between queues. Atlas's organization (categories, queues, sender trust, handling state) is app-owned per ADR 0001, and it is the user's actions inside Atlas that move things, not a background mirror of Gmail.

This is the read-side complement of ADR 0005: just as Atlas does not push its organization back to the provider (the mutation journal covers only sends), it does not pull the provider's ongoing organization in. The two together mean Gmail and Atlas intentionally diverge after ingest, in both directions. Disconnecting an account follows the same principle — already-ingested threads are retained read-only rather than purged. The trade-off is visible inconsistency: mail a user deletes or marks as spam in Gmail lives on in Atlas until they act on it there, which can surprise users who expect the two views to track each other. We accept this because continuous reconciliation of mutable provider state would require diff-syncing every label change, reopen the "app silently reorganizes or removes your mail" problem ADR 0001 exists to prevent, and complicate the forward-only checkpoint model of ADR 0011 for little user benefit.
